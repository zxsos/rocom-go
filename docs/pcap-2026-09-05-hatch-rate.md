# pcap 分析：孵化倍率的工况对照（2026-09-05）

样本 `PCAPdroid_05_9月_15_36_58.pcap`（5.8 MB，1669 条消息，126 种 opcode）。

这是为了回答「孵化倍率到底由什么决定」而抓的**对照样本**：骑乘走动 / 静止 /
挂风场三种工况都有。结论已并入 [data.md](data.md) 3.6，本文留作原始记录与
复现步骤。

另有四份同日样本，交叉验证：

- `PCAPdroid_05_9月_13_26_20.pcap`（3.8 MB，33 次 0x0312）
- `PCAPdroid_05_9月_15_47_58.pcap`（4.1 MB，9 次 0x0312，663 个移动包）
- `PCAPdroid_05_9月_15_58_17.pcap`（3.9 MB，**只有 1 次 0x1344**，无第二次采样
  → 无法做差分，只有移动包有参考价值）
- `PCAPdroid_05_9月_16_07_46.pcap`（7.4 MB，31 次 0x0312、673 个移动包，
  **全程移动无静止**）
- `PCAPdroid_05_9月_16_16_55.pcap`（12 次 0x0312、443 个移动包，按「排除过渡态」
  思路抓的，**最干净的一份** —— 见 §4）

都落在加速日窗口内（周六）。

> **时间口径**：pcapdump 打印的是 **UTC**（`t=07:38:40`），文件名 `15_36` 是本地
> UTC+8。两份 pcap 都落在加速日窗口内（周六）。

## 1. 结论速览

| 问题 | 结论 |
| --- | --- |
| 活动倍率 | 按加速日时间表算，窗口内 **5.00**，不要靠采样反推 |
| 静止时 | **精确 5.00**，多份 pcap 全部样本零方差 —— 这就是活动倍率本身 |
| 移动时 | **中位 21.96**（n=12，标准差 3.38，范围 16.90~27.32）；与速度**无关**；因可能虚报，未折算进 ETA |
| 挂风场 | **不加成**（挂着 1 / 2 / 3 个风场的静止段都是 5.00）；推测是间接的 —— 风场让玩家能持续骑乘移动 |

## 2. 风场在协议里怎么认

`0x0414 ZONE_SCENE_PLAY_ACTS_NOTIFY` 的 **`aura_info_change`**，挂在玩家自己的
`actor_id` 上（其 `logic_id` 就是账号 UID，本例 100000002）：

```
aura_info_change {
  actor_id: 8131259842557902848        ← 玩家自己
  aura_info {                          ← 挂上风场
    id: 148298
    aura_conf_id: 20002                ← 本仓库见到 20002 与 20010 两种
    pos { x: -797775  y: -774871  z: 29689 }
    belong_actor_id: 9284181347180478491
    create_actor_id: 9284181347180478491
    dir: 1800
    radius: 439                        ← UE 厘米,约 4.4 米
  }
}
aura_info_change {
  actor_id: 8131259842557902848
  removed_auras { aura_id: 148298  reason: DAR_NONE(0) }   ← 离开风场
}
```

本份 pcap 共 23 条：`aura_conf_id` 20002 出现 8 次、20010 出现 4 次，其余是
`removed_auras`。同一时刻可挂多个（实测最多 4 个，来自不同 `belong_actor_id`）。

**当前代码没有解析它** —— 因为实测证明风场不影响孵化倍率（见 §3）。判据记在此处，
将来若要单独显示「在风场里」或验证别的效果，从 `0x0414` 取即可。
按 [AGENTS.md](../AGENTS.md) 的「跨区约束要双写」，届时请把上面这段抄进解析函数
的注释里。

## 4. 移动段散布在 17~26

第四份 `16_07_46` 是**全程移动、无静止**的干净样本，6 段 ≥19s 区间都有完整
移动包覆盖（时间覆盖率 100%，无空窗）：

| 时长 | 倍率 | speed 中位 | 停包占比 |
| --- | --- | --- | --- |
| 28s | 27.32 | **126** | 10/10（低速滑行） |
| 32s | 20.62 | 404 | 19/236 |
| 34s | 19.71 | 828 | 5/207 |
| 27s | 18.89 | 1694 | 14/163 |
| 19s | 24.74 | 1726 | 2/23 |
| 19s | 18.16 | 1690 | 8/30 |

**倍率与速度的相关系数 r = −0.46（接近 0，无相关性）** —— 最慢那段（speed 126）
倍率反而**最高** 27.32。结论：移动加成是**固定的开关量**（「在动」就加），不是
随速度变化的连续量。不必按速度插值，也不必区分 `move_mode`。

四份合计 12 个移动段：

| 来源 | 倍率 | speed | 备注 |
| --- | --- | --- | --- |
| 13_26_20 | 16.90 | 904 | |
| 13_26_20 | 25.83 | 714 | |
| 15_36_58 | 23.75 | 898 | |
| 15_36_58 | 22.24 | 583 | |
| 15_36_58 | 25.83 | 371 | |
| 15_47_58 | 21.68 | 900 | 已扣除区间内的静止 |
| 16_07_46 | 27.32 | 126 | |
| 16_07_46 | 20.62 | 404 | |
| 16_07_46 | 19.71 | 828 | |
| 16_07_46 | 18.89 | 1694 | |
| 16_07_46 | 24.74 | 1726 | |
| 16_07_46 | 18.16 | 1690 | |

中位 **21.96**、均值 22.14、标准差 3.38、范围 [16.90, 27.32]。去掉最小最大后
中位仍是 21.96、标准差 2.82 —— **分布是稳的**，不是被个别离群值带偏。

**为什么还是没折算进 ETA**：误差方向不对称。

| 取哪个值 | 遇实际 18.16 | 遇实际 27.32 |
| --- | --- | --- |
| 中位 22.0 | **提前 17%（虚报）** | 推迟 24%（保守） |
| 下限 18 | 提前 ≈0% | 推迟 52%（保守） |

用中位会在低端样本上虚报「快好了」；取下侧值则不虚报、但高速段推迟一半，提示
价值下降。项目一贯的原则是「宁可慢、不虚报可破壳」，故维持：ETA 按活动倍率算，
移动时只提示「实际更快」。

#### 第五份：排除过渡态后，标准差降到 2.05

`16_16_55` 按「先跑起来再取起点」的思路抓，得到**最干净的两段**（时间覆盖
10/10、无空窗，不像 §4 末尾那段 115s 里混着 55 秒静止）：

| 时长 | 倍率 | speed | 停包占比 |
| --- | --- | --- | --- |
| 74s | 20.20 | 813 | 8% |
| 46s | **21.30** | 1221 | **1%** |

**两者只差 1.10** —— 同一份 pcap 内部的重复性远好于跨文件对比，说明之前 3.38
的标准差主要来自「区间里混着静止/过渡」这类污染，而非倍率本身不稳定。

按「覆盖 10/10 且停包 <10%」筛后重算：

| 集合 | n | 中位 | 标准差 |
| --- | --- | --- | --- |
| 全部移动段 | 12 | 21.96 | 3.38 |
| 覆盖完整且停包 <10% | 6 | 20.41 | **2.05** |
| 第五份内部 | 2 | 20.75 | **1.10** |

**但仍不折算**，决定因素是误差方向：

| 取哪个值 | 结果 |
| --- | --- |
| 中位 20.41 | **6 个样本里 3 个会虚报** → 不可接受 |
| 下界 18.89 | 全部不虚报，最多保守 31%（推迟）→ 方向安全 |

用中位有一半样本会提前（虚报「快好了」）；用下界方向安全，但移动 ETA 只比静止
快 3.8 倍、实际能到 4.9 倍，提示价值打折。故维持：ETA 按活动倍率，移动只提示。

> 若将来要折算，取**下界（≈19）**而非中位 —— 这是唯一不虚报的选择。
> 折算前还建议再补 2~3 段同质量的样本，确认下界稳定在 19 附近。

#### 115s 长区间的陷阱

第三份样本里有个 115s 区间，倍率只有 **13.70**，看着像「移动加成变小了」。但按
20 秒分段数移动包会发现**前 55 秒一个移动包都没有**（玩家还没开始跑）：

| 时段 | 移动包 | speed 均值 | 状态 |
| --- | --- | --- | --- |
| …575 ~ …615 | 0 | — | **无移动包（静止）** |
| …615 | 8 | 53 | 起步 |
| …635 | 10 | 457 | 加速中 |
| …655 | 15 | 880 | 跑起来了 |
| …675 | 44 | 930 | 跑起来了 |

扣掉静止那段（55s × 5 倍 = 275 孵化秒）后，剩下 60 秒的真实移动倍率是
(13.70×115 − 275) / 60 = **21.68** —— 与其余样本一致。

> 结论：**统计倍率前必须先确认区间内有没有静止段**，否则会系统性偏低。
> 敏感性：静止段按 50 / 55 / 60s 假设，得 20.39 / 21.68 / 23.19，都落在同一量级。

## 5. 采样粒度：短区间不可信

服务器**约按 5 秒步长**下发进度，故 <10s 的差分区间给出的是假值：

| 时长 | 倍率 | 说明 |
| --- | --- | --- |
| 1s | 5.00 | 未跨步长 → 看着像「没加速」 |
| 1s | 67.50 | 跨了 3 个步长 → 看着像「异常跳变」 |
| 2s | 67.50 | 同上 |

早先正是把这些 67.50 / 130.00 当成「服务器批量补齐的跳变」、想用中位数滤掉 ——
那是被采样粒度骗了。统计倍率时必须剔除 <10s 的区间，§4 的表格已只保留 ≥10s 的。

## 6. 复现

```bash
# 孵化进度采样(25 次,含每颗蛋的 hatched_secs / last_hatch_update_sec)
go run ./cmd/pcapdump -pcap PCAPdroid_05_9月_15_36_58.pcap -op 0x0312 -limit 40

# 移动包(205 条,取 time_stamp 与 speed 向量)
go run ./cmd/pcapdump -pcap PCAPdroid_05_9月_15_36_58.pcap -op 0x0133 -limit 250

# 风场光环(挂在自己 actor_id 上的 aura_info_change)
go run ./cmd/pcapdump -pcap PCAPdroid_05_9月_15_36_58.pcap -op 0x0414 -limit 800 \
  | grep -A14 aura_info_change
```

然后按 `last_hatch_update_sec`（0x0312）、`time_stamp`（0x0133）、
`space_time_ms`（0x0414）三者**统一到秒**后对齐 —— 注意它们单位不同：
`time_stamp` 与 `space_time_ms` 是**毫秒**，需 //1000。三者都是服务器时钟，可直接比。
