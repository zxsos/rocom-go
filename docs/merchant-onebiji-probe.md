## 0. ⚠️ 先读:核心动机已被削弱

本文写作的初衷是「绕开第三方缓存滞后(6~56 分钟)」。但**在挂载过程中发现,
现用源已经开了强制回源**:

```
internal/server/merchant.go:71   merchantForceRefresh = true
```

其注释记录:带 `refresh=true` 后「用户实测整点后**约 1 分钟**即可拿到」新货单。
即**滞后已从 6~56 分钟降到约 1 分钟** —— 当初那个非解决不可的痛点,
现在只剩 1 分钟的量级。

故 onebiji 的**剩余价值**要从「解决滞后」下调为:

1. **无需 token**(现用源 `apii.xianyuw.cn` 需 Token,2026-09-02 实测返回 401);
2. **一次给出全天四档**(现用源只给当前轮),可做提前预告/展示;
3. **交叉验证** —— 用它反查现用源的实际滞后,把「6~56 分钟」这个区间收敛成确切数字。

若只是为了「快 1 分钟」,**不值得换**。是否保留本探测,请据上述三条重新判断。

---

## 1. 背景:要解决的问题是什么

远行商人(游戏内的限时商店,每天 8/12/16/20 点换一轮货)的货单数据,
项目**不自己抓包**,而是取第三方 API 再转发(见 `internal/server/merchant.go`)。

现行方案有个明确的痛点:**第三方缓存滞后**。

轮次整点切换后,第三方返回的货单要滞后 6~56 分钟才从上一轮切成新轮
(实测方法与数据见 `AI_merchant_probe.md`,2026-09-01 的探测)。
为缓解它,`internal/server/merchant.go` 采用的策略是**整点后每 10 秒回源**,
直到拿到本轮为止 —— 有效,但对第三方不够友好,也只是绕过而非解决。

## 2. 现状:两个源,我们用的是哪个

| | 我们现用 | 探测中的替代源 |
| --- | --- | --- |
| 地址 | `apii.xianyuw.cn/api/v1/rocom-merchant` | `onebiji.com/hykb_tools/comm/lkwgmerchant/preview.php?id=1` |
| 形式 | JSON API | **HTML**(已确认无 JSON 接口,`id≠1` 也无数据) |
| 鉴权 | 需 Token(2026-09-02 实测返回 401) | 公开 |
| 单次返回 | 当前一轮 | **全天四档**,每档带 `data-time`(该档结束时间的 Unix 秒) |

**这是两个互相独立的第三方数据源**,不是同一站的两条路 —— 换源等于换数据源,
接入前务必把商品数据核对一遍(见第 6 节的可交叉验证锚点)。

替代源的页面结构参考自 [kanzakine/Roco-API](https://github.com/kanzakine/Roco-API)
(一个 Go 写的快爆工具箱爬虫,带 Server 酱推送)。它的数据本身可用,
但**解析逻辑(选择器)与推送不是我们要参考的** —— 我们已有自己的邮件订阅系统
(`internal/store/subscription*.go`)。值得参考的只有一件事:它的页面里
`data-time` 是**精确的档期结束时间戳**。

## 3. 待验证的假设(本文唯一悬而未决的事)

已知这个源一次给出全天四档。但**它给的是哪一天的**,决定了一切:

| | 行为 | 结论 |
| --- | --- | --- |
| **A** 按天前瞻 | 8:00 开市**之前**,页面就换成了「今天全天四档」 | 开市即有数据,**可绕开滞后** |
| **B** 回顾完整营业日 | 页面始终显示「最近一个已结束的营业日」,8:00 时还显示昨天 | **无用**,滞后问题依旧 |

两者在**换天时刻**就会暴露,**不必等到 8 点开市** —— 这正是本文说
「可以提前验证」的原因:

> 现在(2026-09-02 01:38)页面显示的是 **09-01 全天四档**。
> 盯着它**何时变成 09-02** 就够了:
> - 8:05 之前就切到 09-02 → **A**,假设成立;
> - 到 8:05 仍显示 09-01 → **B**(或它自己也滞后),假设不成立。

## 4. 怎么验证

### 方式一:部署时自动挂(推荐)

服务已内置定点抓取,**默认开启**,部署后自动对准下一个档期整点:

```bash
# 默认即开启;显式关闭用 -slots-capture=false
go run ./cmd/rocom-capture -iface eth0
```

窗口:整点前 2 分钟 ~ 整点后 7 分钟,每 30 秒抓一次,四档(8/12/16/20)通用。
**只打日志**(格式 `[档期抓取 07:58:00] …`),不写文件、不改数据库、不触发通知,
不影响任何业务。查看:

```bash
journalctl -u rocom-capture | grep 档期抓取      # systemd 部署
# 或直接看服务 stdout
```

实现:`internal/server/slots_capture.go`,挂载点 `cmd/rocom-capture/main.go`
的 `-slots-capture` flag。**不做任何判断** —— 只如实记录每个时刻页面上有什么,
结论留给人读日志。

### 方式二:手动跑脚本

脚本已就位:`scripts/probe_onebiji.py`。

```bash
# 监视模式(推荐,可提前跑)—— 每 5 分钟采样,一直运行直到手动停止
cd /workspace && uv run python scripts/probe_onebiji.py --watch

# 试跑 3 次看看输出长什么样(不用等)
uv run python scripts/probe_onebiji.py --watch --interval 1 --max-runs 3

# 单次判定(仅在营业时段 8:00 后有意义)
uv run python scripts/probe_onebiji.py
```

### 抓到的东西存在哪

| 内容 | 位置 |
| --- | --- |
| 解析后的日志 | `~/probe_onebiji.log`(追加,同时打印到终端) |
| **原始页面存档** | `~/probe_onebiji_html/YYYYmmdd-HHMMSS.html` |

存档目录可用环境变量 `ROCOM_ONEBIJI_HTML` 覆盖。

**为什么要存原始 HTML**:解析结果只是"我们的理解",原始页面才是证据。
站点改版导致选择器失效时,只有原始页面能让你看出新结构长什么样。

只在**关键节点**存 —— 单次模式、档期首次出现、档期集合变化时。
不在每次轮询都存:页面约 47KB,1 分钟一次跑 90 分钟就是 400MB,
而那些重复页面里没有新信息。

查看与核对:

```bash
# 看日志
tail -50 ~/probe_onebiji.log

# 看存了哪些原始页面
ls -la ~/probe_onebiji_html/

# 用浏览器打开某次存档(看当时页面长什么样)
xdg-open ~/probe_onebiji_html/20260902-080000.html

# 直接 grep 原始页面验证解析对不对
grep -o 'data-time="[0-9]*"' ~/probe_onebiji_html/*.html
```

**监视模式的判定逻辑**(写在脚本里,这里说明以便核对):
- 只比较「档期集合」(各档的结束时间戳),**不比较商品内容** ——
  要监视的是换天,商品价格微调不该触发报警,否则日志全是噪声;
- 档期集合变化时打印 `*** 档期集合变化 ***` 并列出新旧档期;
- 若新档期**晚于**旧档期 → 判为「已切到新的一天(A)」。

## 5. 怎么解读结果

跑完看 `~/probe_onebiji.log`(或终端输出)。

**若看到 `*** 档期集合变化 ***` 且新档期是 09-02** → A 成立:

```
[07:12:03]  *** 档期集合变化 ***
     旧: 09-01 08:00~12:00, 09-01 12:00~16:00, ...
     新: 09-02 08:00~12:00, 09-02 12:00~16:00, ...
     最新档期结束于 09-02 12:00,距现在 +4.8 小时
     → 页面已切到新的一天(A 按天前瞻,可绕开滞后)
```

记下**切换发生在几点** —— 它直接决定了新方案能提前多久拿到货单。

**若到 8:05 之后仍显示 09-01** → B,或这个站自己也滞后:

- 仍显示 09-01 全天 → 记下它滞后了多久(对比页面第一档的开始时间与当时时间),
  若滞后时间与现用源(6~56 分钟)相当或更久,则**没有替换价值**;
- 已显示 09-02 但没有 08:00-12:00 这一档 → 记下它实际给了哪些档期
  (可能是「已结束的三档 + 当前档缺失」这类中间态)。

**若抓取失败或解析到 0 件** → 站点结构变了,`.all_show` / `.shop_name`
这类选择器失效,需按新的 HTML 结构更新 `scripts/probe_onebiji.py` 的正则。

## 6. 结论出来后:接不接、怎么接

### A 成立(可绕开滞后)

建议**先做备源,不要直接替换**:

- 主源继续用 xianyuw(它是 JSON,稳定、有 Token 约束,反而更可控);
- onebiji 作为**交叉校验**:正好能用它反查主源到底滞后多久,
  把 `AI_merchant_probe.md` 里那个 6~56 分钟的区间收敛成一个确切数字;
- 跑一段时间确认稳定后,再考虑是否倒过来以 onebiji 为主。

接入时要处理:
- **换天/换档的判定改按 `data-time`**,不再依赖第三方自己的"当前轮"字段;
- HTML 解析是脆弱点,选择器失效要能**报错**而非静默返回空
  (参考 `scripts/fetch_rocoworld.py` 的做法:失败率过高直接 `sys.exit`);
- 抓取频率可大幅降低(一天四档,每档抓一次即可),
  现用源那个"整点后每 10 秒回源"的补救可以关掉。

**交叉验证锚点**(确认数据是真的):`docs/data.md` 里记着玩家在远行商人处
买过**神奇的蛋**,而 onebiji 的 20:00-24:00 档里正好有「神奇的蛋 36000 限购 5」。

### B 成立(无替换价值)

删除 `scripts/probe_onebiji.py` 与本文,在 `docs/data.md` 或
`AI_merchant_probe.md` 里补一行结论即可 —— **记下"试过、不行、为什么"**,
免得下一个人再走一遍这条路。

## 8. 注意事项

- **休市时段(0:00-8:00)** 跑单次模式,判定恒为 `NO 页面不含当前进行中的档期`
  —— 那不是失败,是抓早了。单次模式的结论只在 8:00 后有意义。
- ⚠️ **日志里凡是「开市后 X 分钟才拿到」且 X 很大(几百分钟)的记录,都要先怀疑
  是不是测错了对象** —— 拿一个早已开市的档期去测,算出来的"滞后"毫无意义,
  却会被打印成「换源无收益」这类言之凿凿的假结论。
  脚本已加窗口守卫(`now > deadline` 直接拒绝),但它拦不住**已经写进日志的旧记录**。
  拿到一份陌生日志时,先看目标档期与抓取时刻是否合理。
  (2026-09-02 就发生过:日志里混进了这样的记录,已清空。)
- 监视模式需要**长时间运行**。本机(沙箱)不适合挂长任务 ——
  机器不会保留到验证完成,请由使用者在自己的机器上跑,或由下一个 AI 协助。
- 这个站点是**第三方非官方站**,接入前考虑合规与长期可用性:
  它随时可能改版或关停,故即便接入也应能优雅降级回 xianyuw。
